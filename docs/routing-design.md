# Маппинг настроек Zarap на sing-box: outbounds и правила маршрутизации

Статус: предложение, код не написан. Документ фиксирует схему UCI, правила её
преобразования в конфиг sing-box, порядок миграции и границы, которые нельзя
двигать. Реализация разбита на этапы в конце.

## 1. Что не так сейчас

Настройки Zarap не отображаются на модель sing-box, а обходят её.

`/etc/config/zarap` хранит ровно одно подключение, разложенное по опциям секции
`main` (`server`, `uuid`, `public_key`, …), и список секций `client`. Генератор
`sing_box_config()` собирает из этого один outbound с жёстко зашитым тегом
`zarap-proxy` и маршрут:

```json
"route": { "auto_detect_interface": true, "final": "zarap-proxy" }
```

То есть `route.rules` не используется вовсе. Весь выбор «кого проксировать»
живёт в nftables: `zarap_prerouting` заворачивает в TProxy трафик тех IP,
которые попали в набор `zarap_clients_v4`. sing-box же получает конфигурацию, в
которой любой пришедший поток безусловно уходит в единственный outbound.

Из этого следуют ограничения, записанные в README как «ограничения MVP»: один
outbound, никакой маршрутизации по назначению, никакого разделения устройств по
разным серверам.

Цель — сделать так, чтобы настройки Zarap были **описанием** конфигурации
sing-box: список подключений становится `outbounds[]`, список правил становится
`route.rules[]`, и добавление нового вида условия сводится к новому полю в
секции `rule` и новой ветке в генераторе.

## 2. Инварианты

Всё дальнейшее подчинено пяти утверждениям. Любое решение, которое их нарушает,
неверно, даже если удобнее.

**И1. Захват трафика определяется только списком устройств.** Секции `client`
решают, чей трафик Zarap перехватывает. Правило не может добавить устройство в
захват или убрать его оттуда — оно решает только, куда пойдёт уже захваченный
трафик. Это сохраняет текущую связку «отметка в интерфейсе ⇔ набор nftables ⇔
kill switch» ровно такой, какая она есть.

**И2. Kill switch остаётся в firewall для устройства, у которого есть правила.**
Наличие правила ничего не меняет в nftables. Устройство, упомянутое в любом
правиле и с любой целью, остаётся в наборах `zarap_clients_v4` и
`zarap_clients_mac`, попадает в цепочку `zarap_killswitch_forward` и
заворачивается в TProxy наравне с остальными отмеченными. Kill switch
продолжает работать и при выключенном Zarap, и при остановленном sing-box.
Единственное, что снимает его с устройства, — снятие отметки в списке
устройств.

**И3. Цель правила реализуется только в sing-box, никогда в firewall.** Из И2
следует запрет на оптимизацию, которая напрашивается сама собой: при
`target: direct` кажется разумным не заворачивать устройство в TProxy, раз оно
всё равно идёт напрямую. Так делать нельзя. Это открыло бы устройству прямой
путь в WAN через forward и оставило бы его открытым при остановленном sing-box —
ровно то, что kill switch обязан не допускать.

Правильное поведение: трафик заворачивается в TProxy как обычно, sing-box
принимает его и открывает наружу новое соединение от имени роутера. Это
соединение не проходит через forward-цепочку с адресом клиента в источнике,
поэтому kill switch ему не мешает, но существует оно только пока sing-box жив.
Устройство с `target: direct` теряет интернет при остановке прокси — и это
правильный, а не побочный результат.

То же самое касается `target: block`: он не заменяет kill switch и не отменяет
его. Устройство заблокировано дважды и на разных уровнях — nftables не пускает
его напрямую, sing-box отвечает отказом на захваченный трафик.

**И4. Порядок правил значим, первое совпадение выигрывает.** Это семантика
`route.rules` в sing-box, и интерфейс обязан показывать её как есть, а не
прятать за «приоритетами».

**И5. `sing-box check` остаётся последним арбитром совместимости.** Zarap не
закреплён за версией sing-box, поэтому генератор пишет современную форму
конфигурации, а несовпадение со схемой установленного бинарника ловится уже
существующей проверкой и возвращается как `compatibility_error`.

## 3. Схема UCI

```
config zarap 'main'
	option enabled '0'
	option final 'out_1'
	option listen_port '7893'
	option mark '0x5a52'
	option route_table '2022'

config outbound 'out_1'
	option label 'Нидерланды'
	option type 'vless'
	option server 'proxy.example.net'
	option server_port '443'
	option uuid '…'
	option flow 'xtls-rprx-vision'
	option server_name 'cdn.example.net'
	option public_key '…'
	option short_id '…'
	option fingerprint 'chrome'

config outbound 'out_2'
	option label 'Германия'
	option type 'vless'
	…

config client 'dev_001122334455'
	option mac '00:11:22:33:44:55'
	option ip '192.168.1.50'
	option name 'Телевизор'

config rule
	option enabled '1'
	option label 'Телевизор — через Нидерланды'
	list client 'dev_001122334455'
	option target 'out_1'

config rule
	option enabled '1'
	option label 'Гостевой планшет — без интернета'
	list client 'dev_102030405060'
	option target 'block'
```

### Что изменилось в `main`

Поля подключения (`server`, `server_port`, `uuid`, `flow`, `server_name`,
`public_key`, `short_id`, `fingerprint`, `name`) уезжают из `main` в секции
`outbound`. В `main` остаются переключатель, фиксированные ресурсы
(`listen_port`, `mark`, `route_table`) и новая опция `final`.

`final` — куда идёт захваченный трафик, не совпавший ни с одним правилом.
Допустимые значения: имя секции `outbound`, `direct` или `block`.

### Секции `outbound`

Именованные, имя секции — оно же тег в sing-box. Имя выдаёт бэкенд при импорте
ссылки: `out_<n>`, где `n` — наименьшее свободное число. Имя фиксируется в
момент создания и не меняется при редактировании метки или ссылки, потому что на
него ссылаются правила и `main.final`.

Имя секции обязано соответствовать `^out_[0-9]+$`; зарезервированы `direct`,
`block`, `dns`, `main`, `zarap-tproxy`. Проверять это нужно и на импорте, и при
чтении, потому что `/etc/config/zarap` можно отредактировать руками.

Тег `out_1` не читается человеком, а в журнале sing-box фигурирует именно он.
Компенсируется таблицей подключений в интерфейсе, где рядом стоят тег и
`label` — так пользователь может соотнести строку журнала с подключением.
Альтернатива — генерировать тег из `label` — отвергнута: метка обычно приходит
из `#fragment` ссылки кириллицей или эмодзи, слаг из неё пустой, а
переименование секции ломало бы ссылки из правил.

`type` пока всегда `vless`. Опция заведена сразу, чтобы добавление другого
протокола не требовало миграции схемы.

### Секции `client`

Становятся именованными: `dev_<mac без разделителей в нижнем регистре>`. Сейчас
они анонимные (`uci.add`), и сослаться на устройство из правила невозможно.
Содержимое не меняется.

### Секции `rule`

Анонимные, порядок в файле — это и есть порядок правил. `uci.foreach` обходит
секции в порядке файла, а `configure_uci()` и сегодня перезаписывает весь набор
секций целиком, так что перестановка правил в интерфейсе сводится к записи их в
нужном порядке. Отдельного поля `index` нет намеренно: два источника истины о
порядке разъезжаются.

| Опция | Тип | Смысл |
| --- | --- | --- |
| `enabled` | `0`/`1` | Выключенное правило хранится, но не попадает в конфиг |
| `label` | строка | Название для интерфейса, не влияет на генерацию |
| `client` | list | Имена секций `client`; условие «источник — одно из этих устройств» |
| `target` | строка | `out_<n>`, `direct` или `block` |

Условия на первом этапе — только `client`. Поля для будущих условий
(`domain_suffix`, `ip_cidr`, `port`, `network`, `rule_set`, …) добавляются как
новые `list`/`option` в ту же секцию; см. раздел 11.

## 4. Преобразование в конфиг sing-box

### 4.1 Общая форма

```json
{
  "log": { "level": "info", "timestamp": true },
  "inbounds": [
    { "type": "tproxy", "tag": "zarap-tproxy", "listen": "0.0.0.0", "listen_port": 7893 }
  ],
  "outbounds": [ … ],
  "route": {
    "auto_detect_interface": true,
    "rules": [ … ],
    "final": "out_1"
  }
}
```

`inbounds` не меняется. Меняются `outbounds` и `route`.

### 4.2 `outbounds[]`

Каждая включённая секция `outbound` даёт один элемент — ровно то, что сейчас
строит `sing_box_config()`, но с тегом из имени секции:

```json
{
  "type": "vless",
  "tag": "out_1",
  "server": "proxy.example.net",
  "server_port": 443,
  "uuid": "…",
  "flow": "xtls-rprx-vision",
  "tls": {
    "enabled": true,
    "server_name": "cdn.example.net",
    "utls": { "enabled": true, "fingerprint": "chrome" },
    "reality": { "enabled": true, "public_key": "…", "short_id": "…" }
  }
}
```

`flow` и `reality.short_id` опускаются, если пусты — как сейчас.

Дополнительно, **только если на него кто-то ссылается** (цель правила или
`main.final`), добавляется:

```json
{ "type": "direct", "tag": "direct" }
```

Условность существенна для безопасности: если `direct` не объявлен, то опечатка
в теге не может привести к прямому выходу — неизвестный тег отклонит
`sing-box check`, а не молча выпустит трафик в WAN.

Отдельного outbound для `block` **не будет**: специальный outbound `block`
объявлен устаревшим в sing-box 1.11.0 и удалён в 1.13.0, его заменяет действие
правила `reject`.

### 4.3 `route.rules[]`

Каждая включённая секция `rule` даёт ровно один элемент. Условия секции
собираются в поля совпадения, `target` — в способ обработки.

Условие `client` отображается в `source_ip_cidr`: у sing-box нет совпадения по
MAC, поэтому устройство представлено своим статическим IPv4 с маской `/32`.
Именно поэтому статическая DHCP-аренда обязательна — она и есть то, что делает
правило по устройству осмысленным.

Ко всем правилам добавляется `"inbound": ["zarap-tproxy"]`. Сейчас inbound
один, так что поле избыточно; оно ставится сразу, чтобы появление второго
inbound (см. 11.3) не потребовало переписывать все правила.

```
config rule
	list client 'dev_001122334455'
	list client 'dev_aabbccddeeff'
	option target 'out_2'
```

```json
{
  "inbound": ["zarap-tproxy"],
  "source_ip_cidr": ["192.168.1.50/32", "192.168.1.51/32"],
  "outbound": "out_2"
}
```

Отображение `target`:

| `target` | JSON |
| --- | --- |
| `out_<n>` | `"outbound": "out_<n>"` (действие `route` подразумевается) |
| `direct` | `"outbound": "direct"`, плюс объявление direct-outbound |
| `block` | `"action": "reject"` |

`reject` по умолчанию отвечает TCP RST и ICMP port unreachable, то есть клиент
получает внятный отказ, а не таймаут. Поле `method` не выставляется — значение
по умолчанию и есть желаемое; `"method": "drop"` может понадобиться позже и
станет опцией правила.

### 4.4 `route.final`

| `main.final` | JSON |
| --- | --- |
| `out_<n>` | `"final": "out_<n>"` |
| `direct` | `"final": "direct"` + объявление direct-outbound |
| `block` | замыкающее правило `{ "inbound": ["zarap-tproxy"], "action": "reject" }` в конце `rules`, и `"final"` = тег первого включённого outbound |

Единственное место, где отображение не один-к-одному. Причина: `final`
принимает тег outbound, а `block` тегом больше не является. Замыкающее правило
без условий ловит всё, до `final` поток не доходит, но валидное значение там
всё равно нужно — поэтому подставляется первый объявленный тег. Это работает
только потому, что валидация требует хотя бы один включённый outbound всегда
(раздел 6).

### 4.5 Пример целиком

Телевизор — через Нидерланды, гостевой планшет — заблокирован, все остальные
отмеченные устройства — через Германию:

```
config zarap 'main'
	option enabled '1'
	option final 'out_2'

config outbound 'out_1'
	option label 'Нидерланды'
	…

config outbound 'out_2'
	option label 'Германия'
	…

config rule
	option enabled '1'
	list client 'dev_001122334455'
	option target 'out_1'

config rule
	option enabled '1'
	list client 'dev_102030405060'
	option target 'block'
```

```json
{
  "log": { "level": "info", "timestamp": true },
  "inbounds": [
    { "type": "tproxy", "tag": "zarap-tproxy", "listen": "0.0.0.0", "listen_port": 7893 }
  ],
  "outbounds": [
    { "type": "vless", "tag": "out_1", "server": "nl.example.net", … },
    { "type": "vless", "tag": "out_2", "server": "de.example.net", … }
  ],
  "route": {
    "auto_detect_interface": true,
    "rules": [
      {
        "inbound": ["zarap-tproxy"],
        "source_ip_cidr": ["192.168.1.50/32"],
        "outbound": "out_1"
      },
      {
        "inbound": ["zarap-tproxy"],
        "source_ip_cidr": ["192.168.1.61/32"],
        "action": "reject"
      }
    ],
    "final": "out_2"
  }
}
```

## 5. Что происходит с nftables

Ничего. И это главный аргумент за такую границу между слоями.

`zarap_clients_v4` и `zarap_clients_mac` по-прежнему заполняются из полного
списка секций `client`, независимо от правил. `nft_config()`, `sync_live_sets()`,
`live_clients_match()`, цепочки kill switch и защита TProxy-порта не меняются
ни на строчку. Меняется только содержимое `/etc/zarap/sing-box.json`.

Следствия:

- изменение правил не трогает firewall, поэтому вся уже отлаженная транзакционная
  часть `apply_configuration()` — резервные копии, `firewall reload`, сверка
  живых наборов, откат — остаётся как есть;
- устройство с правилом в `block` всё равно остаётся в наборах kill switch.
  Заблокировано дважды и по-разному: nftables не пускает его напрямую, sing-box
  отвечает отказом на захваченный трафик;
- устройство с правилом в `direct` тоже остаётся в наборах и по-прежнему
  заворачивается в TProxy. Наружу оно выходит через sing-box, а не мимо него;
- смена только правил всё ещё требует перезапуска sing-box. Быстрый путь
  «перезапустить только sing-box, не трогая firewall и dnsmasq» напрашивается,
  но выносится в отдельную задачу: он затрагивает логику отката.

### Чего делать нельзя

Перечислено явно, потому что каждый пункт выглядит как разумная оптимизация и
каждый ломает И2:

- исключать устройство из `zarap_clients_v4`/`zarap_clients_mac` по той причине,
  что его правило ведёт в `direct` или `block`;
- добавлять в `zarap_prerouting` обход TProxy для отдельных адресов;
- добавлять в `zarap_killswitch_forward` `return` для устройства, у которого
  есть правило;
- строить наборы nftables из правил, а не из списка секций `client`.

Наборы строятся из списка устройств и только из него. Единственное, что читает
секции `rule`, — генератор `/etc/zarap/sing-box.json`.

### Почему не завернуть в sing-box весь трафик LAN

Напрашивающийся вопрос: если правила всё равно умеют `direct`, зачем вообще
список устройств? Захватить весь исходящий трафик, а решение целиком отдать
sing-box — тогда настройки Zarap отображаются на его модель без остатка.

За такой вариант говорит многое. Слой nftables стал бы статическим: захватываем
весь LAN, наборов, которые надо синхронизировать с содержимым ядра, больше нет.
Это убирает целый класс отказов, который в истории пакета уже случался, —
firewall4 перестраивает цепочки, но не трогает содержимое существующих наборов,
из-за чего снятое с отметки устройство оставалось в них. Правила стали бы
применимы к любому устройству, а маршрутизация по доменам — доступна всем.

Против — четыре довода, по убыванию веса.

**IPv6.** Сейчас внешний IPv6 отмеченных устройств блокируется, а не
проксируется. Для нескольких выбранных устройств это осознанный размен,
записанный в ограничениях MVP. Для всего LAN «заблокировать IPv6» неприемлемо, а
«проксировать» — самостоятельная задача. Захват всего трафика невозможен, пока
не решён IPv6, и это ближайший к блокирующему довод.

**Радиус поражения.** Сегодня отказ sing-box отнимает интернет у отмеченных
устройств и не задевает остальной дом. При захвате всего sing-box становится
единой точкой отказа для всей сети. Отметка устройства — это и есть единица
управления радиусом отказа, и терять её не хочется.

**Различимость kill switch.** «У устройства нет интернета» сейчас — намеренное,
адресное состояние, которое интерфейс объясняет. Если захвачено всё, отказ
выглядит как «интернета нет ни у кого», что неотличимо от неисправности
роутера, и защитный смысл состояния теряется.

**Пропускная способность.** Захваченный трафик проходит через userspace и не
может быть обработан flow offload: tproxy доставляет пакет локально, и
флоутаблица его не видит. Сейчас неотмеченные устройства сохраняют полную
скорость. При захвате всего за это платят все, включая тех, чей трафик уходит в
`direct` и от прохода через sing-box не получает ничего. Величину размена надо
измерять на конкретном железе, а не оценивать на глаз.

Вывод: список устройств стоит понимать не как «кого проксировать», а как «кто
под управлением Zarap». Внутри этой границы правила дают полную выразительность,
включая `direct`; за её пределами Zarap не вмешивается вовсе.

Полностью отвергать вариант при этом незачем — он имеет смысл как явный режим:
`option capture 'selected' | 'lan'` в секции `main`, по умолчанию `selected`.
Тогда захват всего включается сознательно, а не оказывается побочным эффектом.
В первый этап режим не входит: у него в предусловиях IPv6, и его включение
меняет смысл kill switch, а значит, и формулировки в интерфейсе.

### Подмена адреса внутри LAN

sing-box сопоставляет источник по IP. Устройство, назначившее себе чужой
статический адрес, попадёт под чужое правило. Это не новая граница доверия:
kill switch уже сегодня сопоставляет `ip saddr`, и вся модель держится на
статических арендах. Усиление возможно (см. 11.3) и в первом этапе не делается,
но в интерфейсе стоит сказать прямо, что правила по устройствам опираются на
статическую аренду.

## 6. Валидация

Проверки до записи, возвращают `input_error`:

- имя секции `outbound` соответствует `^out_[0-9]+$` и не повторяется;
- поля подключения проходят существующую `parse_vless()` — при импорте ссылки
  она же и порождает секцию;
- включённых секций `outbound` хотя бы одна. Конфигурация без единого outbound
  не имеет смысла и ломает подстановку тега в `final` (см. 4.4);
- `target` каждого правила — это `direct`, `block` или имя существующей
  включённой секции `outbound`. Ссылка на выключенный outbound — ошибка, а не
  молчаливый пропуск;
- каждое имя в `list client` есть среди секций `client`. Правило, ссылающееся
  на снятое с отметки устройство, — ошибка: молча выкинуть его значит изменить
  маршрутизацию за спиной пользователя. Это же и делает И2 проверяемым —
  множество устройств, упомянутых в правилах, всегда является подмножеством
  списка устройств, а значит, целиком лежит под kill switch;
- у правила есть хотя бы одно условие. Роль «всё остальное» принадлежит
  `main.final`, и правило без условий её дублирует;
- `main.final` — `direct`, `block` или имя существующей включённой секции.

Пересечение правил (одно устройство в двух правилах) ошибкой **не** считается:
это законная семантика «первое совпадение выигрывает», и с появлением условий по
доменам пересечения станут нормой. Интерфейс показывает порядок явно и
предупреждает, что второе правило для устройства недостижимо, если первое
покрывает его целиком.

Проверки после генерации не меняются: `sing-box check -c` на временном файле и
`nft -c -f` на временном ruleset, обе уже есть в `validate_candidate()`.

## 7. Миграция

Существующие установки хранят подключение в `main`. Нужен разовый перенос.

Скрипт `root/etc/uci-defaults/91-zarap-routing`, идемпотентный:

1. если `zarap.main.server` пуст или уже есть хоть одна секция `outbound` —
   выйти, ничего не делая;
2. создать `outbound 'out_1'`, скопировав в неё `server`, `server_port`, `uuid`,
   `flow`, `server_name`, `public_key`, `short_id`, `fingerprint`, а `name` — в
   `label`; проставить `type 'vless'`;
3. удалить перенесённые опции из `main`;
4. проставить `zarap.main.final='out_1'`;
5. переименовать анонимные секции `client` в `dev_<mac>`;
6. закоммитить, вернуть `/etc/config/zarap` режим `0600`.

Правила при миграции не создаются. Конфигурация без правил и с `final='out_1'`
даёт ровно тот же сгенерированный маршрут, что и сегодня, — весь захваченный
трафик уходит в единственный outbound. Поведение после обновления пакета не
меняется, и это проверяемое свойство, а не пожелание.

Отдельно: `update_component()` уже снимает резервную копию `/etc/config/zarap`
перед `apk add --upgrade` и восстанавливает её при неудаче, так что неудачное
обновление не оставит наполовину мигрированный конфиг.

## 8. Изменения RPC-контракта

`status` возвращает дополнительно:

```json
{
  "outbounds": [
    { "tag": "out_1", "label": "Нидерланды", "masked_link": "vless://********@…", "in_use": true }
  ],
  "rules": [
    { "enabled": true, "label": "…", "clients": ["dev_001122334455"], "target": "out_1" }
  ],
  "final": "out_2"
}
```

Каждое устройство в `devices[]` получает вычисленное поле `resolved_target` —
тег или `direct`/`block`, который сейчас достаётся ему по правилам. Это то, что
пользователь на самом деле хочет видеть в таблице устройств.

`validate` и `apply` вместо `link` принимают списки:

```
args: { enabled: true, clients: [], outbounds: [], rules: [], final: '' }
```

где элемент `outbounds` — это `{ tag: '', label: '', link: '' }`. Пустой `link`
означает «оставить сохранённый секрет для этого тега», ровно как сегодня пустое
поле ссылки означает «не менять подключение». Так свойство «секреты не
возвращаются в браузер» сохраняется поэлементно.

Замечание к реализации, уже записанное в коде: rpcd строит политику ubus по
*типу* значения-образца в `args`, поэтому образцы обязаны быть настоящими
значениями нужного типа (`[]`, `''`, `true`), а не именами типов.

`restart`, `stop`, `logs`, `updates`, `update_component` не меняются.

### Секреты

`logs()` сегодня вычищает из журнала `uuid`, `public_key` и `short_id` из
секции `main`. После изменения схемы он обязан обходить **все** секции
`outbound` — иначе секреты второго и последующих подключений попадут в
скопированный пользователем журнал. Это самая вероятная ошибка при реализации,
и на неё нужен отдельный тест.

`masked_proxy()` становится функцией от секции `outbound`, а не от `main`.

## 9. Изменения интерфейса

Раздел «Подключение» превращается в «Подключения»: таблица outbound'ов с
колонками тег, метка, замаскированная ссылка и действиями «Добавить»,
«Заменить ссылку», «Удалить». Удаление запрещено, пока на подключение ссылается
правило или `final`, — с указанием, кто именно ссылается.

Новый раздел «Правила»: упорядоченная таблица со столбцами «Вкл», «Название»,
«Устройства», «Куда», кнопками перемещения вверх/вниз и удаления. Под таблицей —
неудаляемая строка «Остальной трафик → [выбор: подключение / напрямую /
блокировать]», которая редактирует `main.final`. Порядок строк — это порядок
правил, и подпись должна говорить, что применяется первое подходящее.

Раздел «Устройства» получает колонку «Куда идёт» из `resolved_target`.

## 10. Тесты

В репозитории уже есть механика, которая для этого и нужна: `lift()` в
`tests/test_parse_vless.py` вытаскивает функции из `zarap.uc` и исполняет их под
настоящим ucode со стабами. Генератор маршрутов тестируется так же.

Новый `tests/test_route_mapping.py` поднимает `sing_box_config()` вместе с
функциями сборки правил и проверяет на разобранном JSON:

- один outbound и пустой список правил дают конфиг, эквивалентный текущему;
- порядок `route.rules` совпадает с порядком секций `rule`;
- `target: block` даёт `action: reject` и **не** создаёт outbound с тегом `block`;
- `direct` объявляется тогда и только тогда, когда на него ссылаются;
- `final: block` даёт замыкающее правило и валидный тег в `final`;
- выключенное правило не попадает в конфиг;
- несколько `client` в одном правиле дают один элемент с несколькими `/32`.

Отдельная группа тестов закрепляет И2 — что правила не протекают в firewall.
`nft_config()` уже поднимается под ucode в `tests/test_nft_rules.py`, туда же
добавляется набор с правилами всех трёх видов целей и проверяется, что при
одном и том же списке устройств сгенерированный ruleset **побайтово совпадает**
независимо от правил: с пустым списком правил, с правилом в `direct` и с
правилом в `block`. Плюс проверка на уровне исходника, что сборщик nftables
вообще не читает секции `rule`.

В `tests/test_contract.py` обновляются образцы `args` и добавляются проверки на
обход всех секций `outbound` в `logs()` и на отсутствие секретов в `status()`.

Браузерные тесты получают фикстуры с двумя подключениями и тремя правилами и
проверяют состав `validate`/`apply`, запрет удаления используемого подключения и
отображение порядка правил.

Отдельно нужен тест миграции: старый `/etc/config/zarap` на входе, ожидаемый
новый — на выходе, и совпадение сгенерированного sing-box конфига до и после.

## 11. Расширение в следующих итерациях

Схема рассчитана на то, что новое условие — это новое поле в секции `rule` и
новая ветка в сборщике правила. Ниже — что именно потребуется, чтобы это не
оказалось сюрпризом.

### 11.1 Условия по назначению: домены, адреса, порты

`ip_cidr`, `port`, `network` (`tcp`/`udp`) добавляются прямо: они отображаются в
одноимённые поля правила sing-box и не требуют ничего от окружения.

Домены — нет. TProxy-inbound видит только IP и порт, доменного имени в потоке
нет. Чтобы `domain_suffix` заработал, в начало `route.rules` нужно правило с
`"action": "sniff"`. Старый путь через `inbound.sniff` объявлен устаревшим в
sing-box 1.11.0 и удалён в 1.13.0, так что сразу делать надо через действие
правила.

Второй слой проблемы — DNS. Сейчас Zarap вообще не трогает DNS: клиенты
резолвят через dnsmasq на роутере, а тот ходит в WAN напрямую. Значит,
маршрутизация по доменам будет работать (снифинг даёт имя из TLS SNI), но сам
DNS-запрос по-прежнему пойдёт мимо прокси. Это отдельное решение — заворачивать
ли DNS клиентов в sing-box, — и его надо принимать явно, а не как побочный
эффект правил по доменам. Там же появится необходимость в
`route.default_domain_resolver`, введённом в sing-box 1.12.0.

### 11.2 Наборы правил (geosite/geoip)

`rule_set` со скачиваемыми `.srs` — самый дорогой пункт: место во flash,
сетевой доступ на роутере, обновление наборов, поведение при недоступности
источника. Схема к этому готова (`list rule_set` в секции `rule` плюс отдельная
секция `config ruleset`), но это самостоятельная задача.

### 11.3 Точное сопоставление устройства вместо сопоставления по IP

Если подмена адреса внутри LAN станет реальной заботой, есть решение, которое
использует существующее разделение слоёв: несколько TProxy-inbound'ов на разных
портах, а nftables выбирает порт по MAC-адресу. Тогда правило сопоставляется по
`inbound`, а не по `source_ip_cidr`, и привязка к устройству становится ровно
такой же надёжной, как записи в наборе `zarap_clients_mac`. Поле `inbound` в
правилах проставляется с самого начала именно ради этого пути.

Это единственное запланированное расширение, которое вообще трогает nftables, и
И2 оно не ослабляет: набор устройств в цепочках kill switch остаётся прежним,
меняется только порт назначения в редиректе. Ни одно устройство при этом не
перестаёт заворачиваться в TProxy.

### 11.4 Режим захвата всего LAN

`option capture 'lan'` из раздела 5 — самостоятельная итерация, а не настройка.
Её предусловие — проксирование IPv6 вместо блокировки; без этого включение
режима отняло бы IPv6 у всей сети. Помимо этого она меняет формулировки в
интерфейсе: при захвате всего отказ sing-box перестаёт быть адресным, и объяснять
пользователю состояние нужно иначе.

### 11.5 Группы outbound'ов

`selector` и `urltest` — отдельная тема: им нужен Clash API или своя ручка в
интерфейсе для переключения, плюс решение, что делать при недоступности всех
участников группы. В схему они ложатся как `config outbound` с `type 'selector'`
и списком тегов.

## 12. Риски и открытые вопросы

1. **Поведение `route.final` при пустом значении** в установленной версии
   sing-box проверено не было. В разделе 4.4 подстановка тега сделана явной
   именно поэтому — чтобы не опираться на неявное «берётся первый outbound».
   Проверить на устройстве при реализации.
2. **Тег в журнале.** `out_1` вместо человеческого имени — осознанный размен на
   стабильность ссылок. Если он окажется неудобен на практике, лечится не
   переименованием секций, а строкой соответствия рядом с журналом.
3. **Отсутствие быстрого пути применения.** Изменение одного правила
   перезапускает dnsmasq и перезагружает firewall, хотя ни то ни другое не
   изменилось. Работает корректно, но медленно; оптимизация — отдельная задача с
   собственным путём отката.
4. **Правило в `block` и kill switch дублируются.** Пользователь может не
   понять, зачем два способа заблокировать устройство. Ответ: снятие отметки
   возвращает устройству прямой интернет, а правило `block` оставляет его под
   kill switch и запрещает даже прокси. Разницу надо объяснить в интерфейсе.
5. **Совместимость версий.** `action: "reject"` требует sing-box 1.11 и новее.
   OpenWrt 25.12.x везёт 1.12.x, так что запас есть, но проверка
   `sing-box check` — единственная гарантия, и сообщение об ошибке должно
   называть минимальную версию.

## 13. Этапы

**Этап 1 — схема и генератор.** Секции `outbound`/`rule`/именованные `client`,
миграция, генерация `outbounds[]` и `route.rules[]` с условием по устройствам,
валидация, обновлённые RPC-аргументы, тесты. Интерфейс показывает подключения и
правила только на чтение. По завершении поведение существующих установок не
меняется.

**Этап 2 — редактирование в LuCI.** Таблицы подключений и правил с
добавлением, удалением и перестановкой; колонка «Куда идёт» в устройствах;
браузерные тесты.

**Этап 3 — условия по назначению.** `ip_cidr`, `port`, `network`, затем домены
вместе с решением по DNS и правилом `action: "sniff"`.

**Этап 4 — наборы правил и группы.** `rule_set`, `selector`/`urltest`.

Границы этапов выбраны так, что каждый заканчивается работающим пакетом:
первый ничего не меняет для пользователя, второй даёт настройку, третий и
четвёртый расширяют словарь условий.
